## 1. Два режима сессии
A. Интерактивный (VS Code, владелец рядом). Задача ставится карточкой (раздел 2). Исполнитель работает сам, спрашивает только по разделу 8. Подтверждения, которые просит Claude Code или страж, владелец отвечает на месте.
B. Автономный (Remote Control с телефона, долгие задачи). Полный контракт на английском с активационной строкой, кодами STOP и строкой возобновления; контракт ссылается на эти правила вместо описания дорожек GitHub и перечисляет точки касания владельца (5.5, 5.6).
Режим выбирает владелец при постановке. По умолчанию: ремонт одной ошибки, тесты, документация = A; многочасовая работа, несколько пакетов, любой R3 = B. Если задача режима A по ходу оказалась R3 (раздел 5.3), исполнитель останавливает дальнейшие изменения и возвращает задачу владельцу для маршрута B; повышение риска не даёт новых полномочий.

## 2. Карточка задачи (режим A)
Пять строк по-русски в чат VS Code: 1) цель (что изменится в поведении); 2) границы (какие пакеты и файлы можно, что нельзя); 3) приёмка (тест, лог, команда); 4) класс риска R1/R2/R3 (раздел 5) или «определи сам»; 5) особое (что спросить до начала).
Исполнитель повторяет карточку одной строкой, затем ОБЯЗАТЕЛЬНО выполняет стартовый контроль (раздел 3) и только потом меняет файлы.
Уточняющие вопросы (гриль, LD-OD-8): только если в карточке не решён вопрос продукта, политики, данных или полномочий. Понятная карточка допроса не требует. В режиме B вопросов нет: при новом существенном решении владельца исполнитель делает STOP с точным вопросом.
Допущения разрешены только для технических деталей (имена тестов, порядок шагов, выбор инструмента) и записываются в отчёт. Полномочия, продуктовые и политические решения, приватность и состав затрагиваемых данных не угадываются: это вопрос владельцу по разделу 8.

## 3. Стартовый контроль (автоматически, без участия владельца)
Перед первым изменением исполнитель проверяет и записывает в отчёт: OS-пользователь claude и путь клона; ветка; git fetch; dev/local существует и содержит origin/release/0.3 (иначе сначала 4.4, пункт «приток»); чистые рабочее дерево и индекс (git status --porcelain --untracked-files=all пустой, кроме перечисленных в 9.2 служебных путей); нет незавершённых операций git (merge/rebase/cherry-pick, lock-файлы); нет другого пишущего агента в клоне (определяется по области и сессии: другая сессия Claude Code или Codex, которая правит этот клон; неактивный сервер Remote Control и проверяющий «только чтение» писателями не считаются); доступность нужных проверок (go, golangci-lint, gofmt, C-компилятор и CGO для -race, python3 для хуков; Codex Security CLI только после квалификации по 5.4); состав пакетов по разделу 14.0 (неутверждённый плагин, хук, MCP или LSP = остановка стартового контроля, не «сообщить и продолжить»); эффективные автор И коммиттер git (git var GIT_AUTHOR_IDENT и GIT_COMMITTER_IDENT), совпадающие с заданными; безопасная тестовая среда (тесты не трогают рабочую базу и рабочие настройки майнера). Любой отказ контроля = остановка с описанием, не «продолжаю на свой страх».

## 4. Ветки, кандидат, слияние, доставка
4.0 Три ветки. release/0.3 — опубликованная стабильная линия в GitHub (защищена ruleset; EXTERNAL_REPORTED, ChatGPT по живому чтению GitHub в октябре 2026: main-protection, ID 19055843, требует Pull Request и проверки lint, build, docker, обходов нет). dev/local — местная ветка накопления проверенных задач на NUC: создаётся один раз от origin/release/0.3 задачей перехода (13.2), в GitHub не пушится до доставки выпуска (4.6). task/<короткое-имя> — ветка одной задачи от свежего dev/local. Так каждая новая задача видит уже принятые исправления, а не старую версию из GitHub.
4.1 Одна задача = одна ветка task/<имя> от свежего dev/local. Коммиты местные, маленькие, осмысленные. История не переписывается; rebase и force push запрещены всегда.
4.2 Кандидат. В начале исполнитель фиксирует BASE = git merge-base dev/local task/<имя> (40 знаков) и записывает его в отчёт как число, а не как метку. Итоговый кандидат = HEAD ветки на момент итоговых проверок, с деревом (git rev-parse HEAD^{tree}) и списком файлов git diff --name-only BASE HEAD. Все итоговые проверки, ревью и сканы относятся к полному изменению BASE..HEAD.
4.3 Чистота кандидата. Непосредственно перед итоговыми проверками, перед независимой проверкой и перед любой передачей владельцу исполнитель заново проверяет: рабочее дерево и индекс чистые (кроме путей из 9.2) и HEAD тот, что записан. Любая правка после этого = новый коммит = новый кандидат, и итоговые проверки повторяются на нём; старые квитанции не переносятся. После выполняемых проверок (тесты пишут кеши) чистота проверяется ещё раз.
4.4 Слияния и полномочия (точное определение для раздела 0).
  Разрешены исполнителю этими правилами без отдельного слова владельца, всегда записываются в отчёт и всегда без rebase и force: (а) «приток»: git merge --no-ff origin/release/0.3 в dev/local, когда опубликованная линия ушла вперёд (владелец слил что-то в GitHub, например Dependabot); (б) «подтяжка»: git merge --no-ff dev/local в task/<имя>, когда dev/local ушёл вперёд относительно BASE. Перед (а) или (б) в отчёт пишутся OLD_BASE, NEW_TARGET, TASK_HEAD (40 знаков) и буквальная команда; после них записывается новая принятая база и новый кандидат, и итоговые проверки (Q2, компонентные, Claude Security для R2/R3, независимая проверка цепочкой по 6.6) повторяются. Конфликт разрешает исполнитель в той же ветке как обычную правку с теми же проверками, но только в файлах границ задачи; конфликт вне границ = STOP с показом файлов. Если живые настройки (.claude/settings.json, страж) направляют команду слияния в ask или deny, действует настройка: ask = точка касания владельца, deny = STOP, без обхода. Бесконфликтное слияние не доказывает правильность поведения.
  Только по слову владельца: (в) «принято»: git merge --no-ff task/<имя> в dev/local после полного отчёта (режим A: на месте; режим B: последняя точка касания, работа заканчивается STOP «ждёт «принято»»); перед (в) исполнитель проверяет, что dev/local не ушёл от записанной BASE, иначе сначала (б) и повторные проверки; (г) слияние в release/0.3 — только кнопкой владельца в GitHub (4.6). Никаких других слияний, cherry-pick, reset и переписывания истории.
4.5 Состояния задачи: ПРОВЕРЕНО МЕСТНО (все проверки класса пройдены, отчёт сдан) → ПРИНЯТО (слито в dev/local по слову владельца). Это полноценный результат задачи режима A и B; ничего не уходит в GitHub (доставка P0, LD-OD-13). Накопленный dev/local хранится копиями по разделу 12, потому что GitHub неотправленную работу не хранит.
4.6 Доставка выпуска (один PR на выпуск, не на задачу; LD-OD-13, LD-OD-16). Только по слову владельца «отправляй выпуск»: исполнитель делает (а) при необходимости, прогоняет Q2 и проверки компонента на HEAD dev/local, пушит ТОЛЬКО dev/local ровно на названный HEAD (git push origin dev/local; не force), создаёт обычный PR dev/local → release/0.3 (не Draft) с телом = перечень принятых задач и их отчётов; если живой .claude/settings.json направляет gh pr create в ask (так было на базе 2026-10-10), это точка касания владельца. Никаких @coderabbitai/@codex комментариев и ожиданий внешних дорожек. CI (lint, build, docker) идёт сам. Состояния: ВЫПУСК ОТПРАВЛЕН, CI ОЖИДАЕТСЯ → CI ПРОШЁЛ / CI ПРОВАЛЕН → СЛИТО ВЛАДЕЛЬЦЕМ (кнопка в GitHub; фактически слитый коммит записывается) → РЕЛИЗ → ОБНОВЛЕНО НА TRUENAS. При провале или неизвестном CI слияния нет: починка задачей по разделам 2–6, новое «принято», новый push по новому слову. Пока репозиторий открыт, доставка публикует код.
  Релиз и обновление TrueNAS идут по действующему процессу Master §17, не по этим правилам. ФАКТ (stable-release.yml в копии репозитория, прочитан 2026-10-21): workflow запускается тегом stable-vX.Y.Z, требует, чтобы коммит тега лежал в release/X.Y, и требует ЗАРАНЕЕ созданный владельцем опубликованный пустой Release на этот тег (не draft, не pre-release, без файлов, создан с make_latest=false); затем сам проверяет код, собирает образ и публикует его в ghcr как bukerov-twitch-miner-go-stable:X.Y.Z. Номер версии и линия (release/0.3 или новая release/0.4) выбираются владельцем по Master §17, исполнитель их не придумывает. Перед первым выпуском отдельно проверяется путь обновления на TrueNAS (откуда контейнер берёт образ, где база и настройки, как откатиться); наличие образа в ghcr само по себе обновления не доказывает. Пока майнер дорабатывается, теги stable-v* не пушатся (LD-OD-12).
  Образы ghcr, из которых сейчас развёрнут контейнер на TrueNAS, не удаляются, пока владелец не принял проверенную замену с откатом (N3; LD-OD-11 отложено). Скрытие старых Release (LD-OD-10) — отдельная операция владельца вне очереди разработки; перед следующим выпуском проверяется, что шаг workflow «releases/latest» находит опубликованный релиз (ФАКТ: шаг сравнивает только имя тега; при всех релизах в черновиках запрос даёт ошибку и выпуск падает).

## 5. Классы риска и проверки
5.1 Q2 (обязательный набор, настоящие коды выхода, на итоговом кандидате):
  git diff --check BASE HEAD
  git diff --check
  gofmt -l .   (код выхода 0 И пустой вывод)
  GOTOOLCHAIN=local go mod verify
  GOTOOLCHAIN=local go vet ./...
  GOTOOLCHAIN=local go build ./...
  TZ=UTC GOTOOLCHAIN=local go test -race -count=1 ./...
  TZ=UTC GOTOOLCHAIN=local go test -count=1 ./...
  GOTOOLCHAIN=local make lint
BASE и HEAD в командах исполнитель подставляет как 40-значные значения до запуска; владелец эти шаблоны в терминал не копирует. Оба прогона тестов обязательны (под -race часть тестов пропускается). Ориентир на NUC (OWNER_REPORTED 2026-10-20): тесты 74 с + race 88 с + остальное, около трёх минут на полный Q2; это ожидаемое время, не тайм-аут. Один тяжёлый прогон за раз.
5.2 Проверки изменённого компонента, помимо Q2 (обязательны, если компонент тронут): Python-хуки и установщики (.claude/hooks/*.py) — их unittest-наборы (python3 -I -m unittest discover -s .claude/hooks -p 'test_*.py') и, для установщиков, прогон на копии; конфигурация и настройки — разбор файла и проверка эффекта; существующий веб-интерфейс — проверка в браузере по правилам Dashboard, даже пока новые браузерные инструменты отложены (14.6); миграции SQLite — тест на копии базы с откатом; упаковка (Dockerfile, workflow) — на NUC Docker нет, поэтому задача помечает «сборка образа не проверена местно», а проверкой служит CI docker при доставке выпуска (4.6); сама упаковка и workflow — R3. Отсутствие любой другой нужной проверки = НЕДОСТУПНО/остановка, не PASS.
5.3 Классы. Класс определяет исполнитель по содержанию изменения, не по типу файла, и повышает при сомнении; понизить может только владелец.
  R1 (низкий): документация, сообщения, тесты, не меняющие проверяемое поведение, конфиги без влияния на поведение. Claude Security по 5.5 обязателен для любого изменения кода и файлов, влияющих на безопасность (Go, тесты, хуки, workflow, Dockerfile, настройки, шаблоны и ассеты веб-интерфейса), в любом классе; для чисто текстовых изменений (документация, сообщения) он помечается «не применим: нет кода» с причиной. Класс никогда не отменяет скан изменённого кода. НЕ R1: удаление или ослабление утверждения в тесте, изменение команд восстановления или отката, любое изменение прав и инструкций агентов (CLAUDE.md, CLAUDE.local.md, AGENTS.md, .claude/settings*.json, хуки) — это R3.
  R2 (средний): рабочий Go-код без параллелизма, сети, авторизации, схемы БД и хуков.
  R3 (высокий): параллелизм (goroutine, каналы, мьютексы), сеть и протокол Twitch, токены и авторизация, схема и миграции SQLite, настройки, хуки, страж, наблюдатель, деплой, инструкции и права агентов.
  Проверки по классам:
  R1: Q2 + проверки компонента (5.2) + одна независимая проверка (раздел 6) + Claude Security, если тронут код (см. выше).
  R2: R1 + для ошибок сначала падающий тест (RED), потом починка (GREEN), по 5.7 + Claude Security на BASE..HEAD (5.5).
  R3: R2 + фальсификаторы для каждого изменённого механизма по 5.7 + дифф читает дорогая модель сама + «принято» владельца (4.4в) только после показанного полного отчёта. Codex Security CLI в приёмку R3 НЕ входит, пока не квалифицирован (решение владельца LD-OD-15: позже, в очередь); после квалификации он добавляется в R3 как обязательная дорожка новой ревизией этих правил. До тех пор в отчёте стоит строка «Codex Security: не квалифицирован, не запускался», и это не НЕДОСТУПНО и не оговорка к приёмке. Прежняя дорожка Codex Security на GitHub для каждого PR этими правилами снята (раздел 0). Последствие и объём (LW3-B01): до квалификации все задачи R3, включая сеть, авторизацию, страж и хуки, принимаются без второго сканера безопасности; это сокращение проверок по сравнению с прежним процессом, а не равноценная замена. Рекомендация ChatGPT (записана как отвергнутая владельцем альтернатива LD-OD-15): квалифицировать сканер до приёмки серьёзных изменений сети, авторизации и защитных механизмов. Владелец может в любой момент поднять квалификацию в очереди одним словом.

## 6. Независимая проверка (по agent-watchdog, LD-OD-7)
6.1 Одна квалифицированная независимая проверка закрывает требование для всех классов (без дублей). Проверяющий всегда не автор: автор Claude Code → проверяет Codex (/review против BASE); если Codex недоступен — подагент Claude Code с чистым контекстом (без отчёта автора на входе), и это пишется в отчёт; автор Codex → проверяет Claude Code. До ввода раздела 11 автор всегда Claude Code. Проверяющий работает только на чтение и никогда не становится вторым писателем.
6.2 Проверяющий получает карточку, BASE, HEAD, полный дифф BASE..HEAD и доступ к репозиторию, а НЕ отчёт автора в первую очередь. Записи Task Observer проверяющему не передаются. Порядок: сначала собственные ожидания и гипотезы по карточке и диффу, потом чтение отчёта автора, потом сверка: что просили, что заявлено, что реально изменилось, что проверено.
6.3 Тип замечания: Пробел / Баг / Слабое доказательство / Уход от задачи / Претензий нет (с указанием, что проверено и верно).
6.4 Решение по каждому замечанию отдельно от типа: подтверждено (да/нет, с уликой) → существенность (блокирует / важно / мелочь) → входит в задачу (да/нет) → исход (исправлено / отложено с причиной / решение владельца / маршрут в другую задачу). Правила исхода: невыполненный критерий приёмки, недоказанная обязательная защита и любой подтверждённый дефект правильности или безопасности в рамках задачи с существенностью «блокирует» или «важно» чинятся в той же ветке без вопросов владельцу; отложить такой дефект может только владелец явным решением; переименование «блокирует» в «важно» приёмку не открывает. Тест, без которого не доказан критерий приёмки, отложить нельзя. Необязательные улучшения и тесты сверх приёмки откладываются с причиной и перечисляются. Дефект вне задачи получает маршрут (запись в очередь), не расширение задачи.
6.5 Замечания идут одной ранжированной запиской на контрольной точке, не по одному посреди работы; исключения: дефект в коде, который автор правит прямо сейчас, или ответ на вопрос, на котором автор застрял.
6.6 Повторная проверка после исправлений идёт цепочкой: исходная полная проверка + дифф исправлений + затронутое ими поведение (вызывающий код, инварианты) + итоговая квитанция, привязанная к новому HEAD. Проверка только изменённых строк не считается итоговой. Если исходная полная проверка или цепочка недоступны, проверка делается полностью заново. Полировка неизменённого кода прекращается; ни одна проверка не отменяется.
6.7 Остановка. Неразрешённый блокирующий дефект, недоступный обязательный инструмент, исчерпанная квота или отсутствие продвижения = STOP с контрольной точкой (раздел 9), а не «принято с оговоркой». Численный предел раундов не устанавливается; ограничение в 6.6.
